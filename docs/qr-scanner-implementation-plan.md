# QR Scanner Implementation Plan — Camera and Gallery

Status: implemented in SIMRS A and SIMRS B; automated frontend/build checks pass. Physical camera/browser acceptance remains to be recorded.
Prepared: 2026-10-30.
Applies to: SIMRS A and SIMRS B, for QR Masuk and QR Keluar.

## 1. Objective and agreed workflow

Enable hospital staff to process a patient's JejakJKN QR through either a live camera or an image selected from the device gallery.

1. Open **Pindai QR** and select **QR Masuk** or **QR Keluar**.
2. For SIMRS B check-in, optionally enter the hospital visit reference before scanning.
3. Choose **Buka kamera** or **Pilih dari galeri**.
4. Read one QR from the camera or selected image, stop capture/decoding, and submit it through the existing SIMRS scan API.
5. Show **Memproses QR…**, followed by the backend-confirmed result or an actionable error.
6. Staff explicitly choose **Pindai berikutnya**, **Coba lagi**, or **Buka kunjungan**.

Implementation assumption: successful camera/gallery decoding automatically starts processing; it does not require copying the token or pressing a second submit button. The selected IN/OUT mode is explicit and must never switch automatically based on untrusted QR content. Manual paste remains an alternative and retains its **Proses QR** button.

This supersedes the earlier camera-only proposal that populated the token field and required a separate processing click.

## 2. Current project context

- Patient Web already uses `qrcode.react` to display the token returned by Encounter Service. It supports check-in, check-out, and post-checkout summary responses.
- Both SIMRS scan screens currently contain visual camera placeholders. Their working scan path uses pasted tokens.
- SIMRS A owns visit worklists, clinical records, corrections/cancellations, delivery retry, exceptions, and claim submission to the separate BPJS claim simulator.
- SIMRS B has its own API schema, local catalog and quantity translation, visit worklists, check-out, delivery retry, and claim submission.
- Verifier Web has claim intake, CSV processing, verification, human review, and AI summaries. Camera scanning must not modify these workflows.
- SIMRS browsers call their simulator backend. Backend credentials and facility authorization remain server-side.
- Each current frontend `scan()` call creates a new idempotency key. Automatic scanning requires a stable attempt identity and an immediate duplicate-submission guard.
- Both app controllers poll data every two seconds. Polling must not recreate the scanner or replace an active attempt.
- `src/design/View.tsx` files are generated by `scripts/design-to-tsx.mjs`; permanent integration must survive regeneration.
- The older `tests/e2e/test_three_simulators.spec.ts` targets superseded UI labels. Newer `demo-ui.mjs` and `demo-ui-batch.mjs` describe the redesigned screens and should inform its update.

Observed baseline during the preceding review: SIMRS A's 12 tests and SIMRS B's 11 tests passed; both production builds passed. These tests are primarily render checks and do not establish camera or full workflow correctness.

## 3. Boundaries and invariants

### In scope

- Camera preview, start/stop, device selection, and permission/error handling.
- Gallery image selection and local QR decoding.
- One submission pipeline per app for camera, gallery, and pasted tokens.
- Duplicate-frame suppression, retry identity, source cancellation, and resource cleanup.
- Scan-specific API error messages and reliable success rendering.
- Generated-view integration, dependency/build wiring, automated tests, and manual instructions.

### Preserved behavior

- Existing scan endpoints, request field names, token purpose, expiry, signatures, tenant binding, Redis reservation, and durable receipts.
- Clinical records, outboxes, synchronization watermark, patient summary gating, claims, verification, and review.
- Manual token input, documented exceptions, and the patient's existing simulator shortcut.
- Backend verification is the authority. Reading a QR is not proof that it is valid, unexpired, unused, or belongs to the selected facility.
- No database migration or public API contract change is expected.

### Excluded from this task

Continuous batch redemption, offline redemption queues, QR generation redesign, image history, cloud image processing, native mobile apps, and a broader frontend rewrite.

## 4. Component and decoding design

Use `qr-scanner` as the proposed decoder for both video and still images. Confirm and pin the chosen package version in lockfiles during implementation. Bundle its worker locally and lazy-load decoding only when a source is selected. Native `BarcodeDetector` alone is insufficient as the cross-browser implementation.

Create one small shared typed component/module under `libs/web-qr-scanner/`, with thin app-specific callbacks. It owns capture/decoding only; it must not know facility codes, API credentials, clinical records, or claim state.

Suggested component contract:

- `disabled`: prevent source activation during submission.
- `onDecoded(value: string)`: emit at most one token for the current source session.
- `onError(error)`: report a local acquisition/decode error, separate from backend errors.
- `resetKey`: changing mode or starting another scan invalidates the current session.

Keep request-attempt state in each existing app controller, where facility-specific request construction already belongs. Avoid introducing an application-wide state library.

The apps currently build from separate Docker contexts. Package the shared source as a local file dependency and adjust only the two SIMRS build contexts/Dockerfiles to include it. Verify local `npm ci`, TypeScript resolution, Vite worker output, and Docker builds. Do not leave imports pointing outside a container's build context or install a second React runtime in the shared package.

### Camera path

- Ask for camera permission only after **Buka kamera** is pressed; never request microphone permission.
- Prefer the rear-facing camera, with a usable default-camera fallback.
- Use a muted inline video preview and a visible scan region.
- Offer device selection after permission is granted; stop the old stream before switching.
- Treat frames without a readable QR as normal scanning, not repeated error alerts.
- On the first accepted decode, lock the session immediately and stop the stream before submission.
- Do not restart scanning after success or failure without an explicit user action.

### Gallery path

- Use a single-file image picker without a forced `capture` attribute, so it can open the gallery/file browser independently of camera capture.
- Initial supported formats: JPEG, PNG, and WebP. Show guidance to export a screenshot as PNG/JPEG if the browser cannot decode a selected format such as HEIC.
- Proposed limits: 10 MiB per file and 20 megapixels after image decode. Check size before decoding and dimensions before scanning; report an error instead of freezing the page.
- Stop the camera and invalidate its callbacks before opening the picker.
- Decode the selected image locally. A selected file must never be uploaded to a server.
- Cancellation is not an error. Clear the file input after handling it so selecting the same file again works.
- Revoke object URLs, close image bitmaps where used, and release temporary image/canvas references on completion or cancellation.
- Use one patient QR per image. The initial decoder is not a multi-code selector; explicitly instruct staff to crop images containing multiple codes and do not claim that all multi-code images can be detected or rejected.
- A QR screenshot retains the original token's 60-second validity. Importing it does not refresh expiry or allow reuse.

## 5. Submission, idempotency, and state transitions

States: `IDLE`, `STARTING_CAMERA`, `SCANNING`, `READING_IMAGE`, `SUBMITTING`, `SUCCESS`, `ERROR`.

1. Capture mode and optional visit reference when starting a source session.
2. Decode a non-empty bounded string. Perform only basic input checks; never navigate to a decoded URL, evaluate content, or treat client-side JWT parsing as validation.
3. Acquire a synchronous submission lock before any asynchronous operation or React state update. This protects against two frames or a frame and a manual click arriving together.
4. Create an immutable attempt containing mode, token, idempotency key, and the complete request payload, including any generated visit reference.
5. Submit exactly once through the existing scan helper. Disable source buttons, manual submission, and mode/reference changes while the request is pending.
6. For an uncertain transport failure, allow explicit retry using the exact same key and payload. Retain the attempt in memory only. Do not queue offline or repeatedly retry automatically.
7. Backend expiry/consumption rules still apply to retries. Do not weaken token validation to make a late retry succeed; reconcile from the worklist or request a fresh QR as appropriate.
8. A different token, mode, or reference creates a new attempt. Clear token material when the attempt is discarded, completed, or the screen is left.
9. Keep the returned `encounter_id` on success. If refreshing the worklist fails, show that success and a refresh action; never fall back to displaying an unrelated first visit.

Existing endpoint mapping:

| App | Check-in | Check-out | Token field |
|---|---|---|---|
| SIMRS A | `/api/scan/check-in` | `/api/scan/check-out` | `qr_token` |
| SIMRS B | `/api/pindai/masuk` | `/api/pindai/keluar` | `token_qr` |

Change the frontend helpers to accept a prepared attempt/request identity instead of generating a fresh key on each retry. Search and update every caller, including demo actions and tests. Existing backend request schemas remain intact.

## 6. Lifecycle, privacy, and errors

- Stop media tracks and decoding on navigation, mode changes, source changes, document hiding, unmount, and successful decode.
- Use a generation/session counter to ignore callbacks from cancelled camera startup, image decoding, or a previous scan. If permission resolves after cancellation, stop the returned stream immediately.
- Stop the camera when the tab becomes hidden; require an explicit restart when returning.
- Preserve business data polling independently from scanner lifecycle. Keep callback identities stable where needed so normal rerenders do not reinitialize capture.
- Never log raw tokens, image contents, or camera frames, and never persist them to local/session storage. Disable or redact browser traces/screenshots in sensitive scan tests where they would retain valid tokens.
- Provide keyboard-accessible controls, visible focus, labelled video/file input, `aria-live` status, and alerts for actionable errors.

| Failure | User-facing behavior |
|---|---|
| Permission denied | Explain how to enable camera access; retain gallery and paste alternatives. |
| No camera / device busy | Explain the device problem and offer another source. |
| Insecure origin | Explain that camera use needs localhost or trusted HTTPS. |
| Bad/oversized image or unsupported format | Explain the accepted formats/limits and allow another selection. |
| No readable QR | Ask for a sharper image containing one complete QR, with white margins. |
| Expired token | Ask the patient to display a fresh QR. |
| Already consumed | Ask staff to check the recorded visit before starting another scan. |
| Wrong purpose | Explain the selected mode and request the corresponding QR. |
| Invalid signature / facility mismatch / invalid encounter state | Display the actual backend rejection; do not label it as an outage. |
| Uncertain request result | Offer same-attempt retry and worklist reconciliation. |

Both clients currently simplify error parsing. Inspect the actual nested FastAPI `detail` and problem responses, then normalize only the scan error path without changing unrelated clinical/claim behavior. Add missing SIMRS B messages rather than mapping every rejection to `DOWN`.

## 8. Environment support

- Local desktop webcam: use the existing localhost app addresses.
- Remote phone/tablet access: serve the scanner through trusted HTTPS and configure reachable API origins, CORS, and any proxy routes consistently. `localhost` on the phone points to the phone itself.
- HTTPS pages must not call the existing HTTP API URLs as mixed content. Prefer scoped same-origin proxy routes when preparing an HTTPS demo deployment.
- Do not use browser insecure-origin flags or wildcard CORS as the supported setup.
- Keep gallery/manual input available when camera APIs are unavailable, provided the remaining app APIs and secure-context-dependent request helpers are supported.
- Browser acceptance targets: desktop Chrome/Edge and Firefox, Android Chrome, and iOS Safari. These are testing targets, not a claim that hardware testing has already passed.

## 10. Required acceptance matrix

| ID | Test | Expected result |
|---|---|---|
| SCAN-01 | Camera QR IN and OUT in A and B | Correct facility visit created/closed after backend acceptance. |
| SCAN-02 | Gallery QR IN and OUT in A and B | Same backend behavior as camera; no image upload. |
| SCAN-03 | Actual decoder processes a generated signed-token QR image | Decoded string equals the original token; fallback worker path also tested. |
| SCAN-04 | Repeated frames and simultaneous manual click | One request attempt, one durable redemption, no duplicate visit. |
| SCAN-05 | Lost response after backend commit, then retry | Same key and payload; receipt replay where token validity permits. |

| SCAN-10 | Polling, rerenders, mode changes, tab hiding, unmount | Stable scanner state; capture stops when required. |

Use mocked media devices for deterministic lifecycle tests and a real generated QR fixture for decoder correctness. For browser integration, feed generated frames through a test media stream or fake video device; do not count a stubbed `onDecoded` callback alone as camera verification. Obtain fresh backend tokens for live tests so expiry failures are intentional.

Relevant existing commands: app-level `npm test` / `npm run build`, `make test-contract`, `make test-integration`, `make test-security`, `make test-concurrency`, and `make test-e2e` after updating its UI journey. Run tests against local synthetic data; no reset of shared data is required by this plan.

## 11. Delivery and rollback

Deliver the camera/gallery implementation, updated tests, regenerated views, reproducible dependency locks, and operator instructions together. Completion requires the automated acceptance checks to pass and hardware coverage to be reported honestly.

Keep changes in a focused reviewable change set. With no database migration, rollback restores the prior frontend/build configuration and manual-token UI without changing visit, evidence, claim, or review data. Any optional HTTPS configuration must have its own documented reversal steps.

Residual limitation: a photographed/shared QR can still be used within its valid window by an authorized scanner. Camera/gallery acquisition does not strengthen the existing physical-presence assurance; signature, expiry, nonce, and facility controls remain the protection.
